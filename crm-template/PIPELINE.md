# PIPELINE — как сырая переписка становится очередью «кому писать сегодня»

`ENGINE.md` объясняет **модель**. Этот файл — про **проводку**: откуда берётся каждое
число, что именно шипнуто в `reference/`, а что тебе придётся написать самому под свою
платформу. Он написан после того, как внешний ревьюер сказал прямо: «карта обещает
готовый движок, а слоя извлечения сигналов нет — чужой агент это прочитает, но не
воспроизведёт». Справедливо. Вот недостающая часть.

## 0. Проверь за 10 секунд, что оно вообще живое

```bash
cd crm-template/reference
python temperature.py selftest    # модель + регрессии на реальные грабли
python budget.py selftest         # гонка и окно краха
python demo.py                    # весь движок на 54 приложенных карточках
```

`demo.py` — не картинка, а замер: он пересчитывает приложенный экспорт и сравнивает
с тем, что насчитала живая система. Результат на сегодня: **полоса совпадает 54/54
(100%), приоритет проседает в среднем на −6.5 (худший случай −16)**. Это и есть
ответ на вопрос «сколько тут работает без слоя сообщений»: доска Hot/Warm/Cold —
работает, очередь «кого будить первым» — нет. Отсюда и порядок стройки.

## 1. Четыре стадии

```
  СЫРЬЁ                ФАКТЫ                  ЧИСЛА                 ДЕЙСТВИЕ
  чаты, звонки   ->    leads + messages  ->   temperature.py   ->   safe_send.py
  контакты             (SQLite)               (ночью, 0 токенов)    (бюджет + аудит)
       |                    |                        |                    |
   адаптер под         schema.sql              reference/            reference/
   платформу           (шипнуто)               (шипнуто)             (шипнуто)
   ТЫ ПИШЕШЬ САМ
```

Шипнуто три стадии из четырёх. Первая — твоя, и это осознанно: адаптер намертво завязан
на платформу (Telegram/Discord/X/почта), у каждого свой API и свои правила. Зато контракт
между стадиями узкий, и он описан ниже целиком.

## 2. Контракт: какой сигнал откуда берётся

Это тот самый список, который `demo.py` меряет. Первые четыре поля живут в таблице
лидов, последние три — только в хранилище сообщений, и без них приоритет врёт.

| Поле | Откуда | Кто читает | Есть в `sample-leads.json`? |
|---|---|---|---|
| `status`, `category` | руками / из старой CRM | только `Archived`-ветка | ✅ |
| `n_calls` | календарь или транскрипты звонков | `depth`, `call_rec` | ✅ |
| `first_contact` | минимум по всем событиям | `memory` (полураспад 365д) | ✅ |
| `last_contact` | максимум по всем событиям | ⚠️ только как fallback | ✅ |
| `last_inbound` | **их** последнее сообщение | `recency`, `resurgence` | ✅ |
| `n_lead_msgs` | счётчик **их** сообщений | `depth`, `frequency` | ✅ |
| `last_outbound` | **наше** последнее сообщение | **`penalty`** | ❌ нужен message store |
| `n_our_msgs` | счётчик **наших** сообщений | `frequency` | ❌ нужен message store |
| `last_call` | дата последнего звонка | `call_rec` | ❌ нужен календарь |

⚠️ **Главная ловушка этого контракта.** `last_contact` — это «последнее касание любого
рода», включая наш собственный неотвеченный DM. Если подставить его туда, где нужен
`last_call` или `last_inbound`, то вчерашнее наше сообщение сделает двухлетний звонок
«свежим», и человек, который давно молчит, всплывёт наверх как Hot — агент пойдёт его
дожимать. Это ровно та ошибка, которую нашёл внешний ревьюер; в `temperature.py` она
закрыта отдельной регрессией (`ghost` в selftest), но в СВОЁМ адаптере ты можешь
завести её заново. Правило: **никогда не подставляй в сигнал «что сделали они» то, чем
управляем мы.**

## 3. Что должен делать адаптер (стадия 1)

Минимальный контракт — четыре функции. У нас их реализация завязана на Telethon и в
пакет не входит; интерфейс от платформы не зависит.

```python
identity(raw_contact) -> {"handle": str, "platform_id": str, "name": str}
    # стабильный id важнее хэндла: хэндлы меняются, id нет

history(platform_id)  -> [{"ts": iso, "direction": "in"|"out", "text": str}, ...]
    # ровно отсюда берутся last_inbound / last_outbound / n_lead_msgs / n_our_msgs

limits()              -> {"daily_cap": int, "min_pause_s": int, "max_pause_s": int}
    # что платформа терпит; для нас это 3-5 в день на аккаунт

send(platform_id, text) -> ok | FloodWait(seconds) | error
    # ЕДИНСТВЕННОЕ место, которое реально пишет людям
```

Дальше сворачиваешь `history()` в счётчики и даты (одним проходом, `GROUP BY`), пишешь
в `leads`, и `temperature.py` работает.

## 4. Приватность экспорта

`sample-leads.json` — не «база с заменёнными именами». Замена имён недостаточна: **роль +
страна + точные даты + счётчики** вместе образуют квазиидентификатор, по которому редкую
комбинацию можно сопоставить с публичным профилем. Поэтому в приложенном экспорте:
роль и страна **удалены**, даты **огрублены до месяца**, идентификаторы синтетические.
Полный перечень — в блоке `_privacy` внутри самого JSON.

Если будешь делать свой экспорт для чужих глаз — сначала спроси, какие поля модель
реально читает, и выкинь всё остальное. Модели тут нужны только даты и счётчики.
Ради этого `days_since()` понимает и `YYYY-MM`, а не только полную дату.

## 5. Чего в пакете НЕТ (чтобы не искал)

- **Адаптер платформы.** Стадия 1 целиком, см. §3.
- **Ночной раннер.** У нас это задача планировщика, которая гоняет пересчёт по всей базе
  и перестраивает дашборд. Тут только чистая функция скоринга — оборачивай как удобно.
- **Слой разрешения личностей.** Таблица `people` в `schema.sql` описана, код слияния
  дублей не приложен (он у нас плотно завязан на наши источники).
- **Копирайтинг.** Ни один файл здесь не пишет текст сообщения. Это осознанная граница:
  «кто решает, что сказать» и «кому разрешено нажать send» — разные модули, и в этом
  половина безопасности.
- **Веса, доказанные экспериментом.** 0.35/0.20/0.25/0.20 и полураспады пришли из
  внешнего ресёрча. A/B их не проверял. Бери как отправную точку, а не как истину.

## 6. Порядок стройки, если начинаешь с нуля

1. `schema.sql` → пустая база. 5 минут.
2. Адаптер: `identity` + `history`, залить исторические чаты, посчитать счётчики. Это
   самый долгий шаг и единственный по-настоящему платформенный.
3. `temperature.py` ночью по всей базе → у тебя появилась доска Hot/Warm/Cold. По замеру
   `demo.py` она честна уже на этом шаге.
4. Только теперь `budget.py` + `safe_send.py` + `send`. Отправку включай последней и
   с маленьким лимитом: всё, что до неё, обратимо, а это — нет.

# Шаблон — мета-промпт «разрежь задачу правильно» + pre-flight чек

> 🧒 Что это: готовый текст, который Антон (или я от его лица) даёт **лид-сессии ИИ ПЕРЕД тем, как открывать параллельные окна**. Заставляет ИИ разрезать задачу на реально непересекающиеся части, сам себя проверить, и выдать pre-flight таблицу коллизий. Синтез гетеро-DR (ChatGPT+Gemini+Grok), DR26-07-05-HUB-04. Решение: decision-decomposition-cut-quality-and-lifecycle [internal]. Механика вокруг: [[reglament-dekompozitsiya-zadachi-na-parallelnye-sessii]].

## Когда применять
Крупная задача, которую хочется вести в 3–5 параллельных сессиях. Сначала — этот промпт лид-сессии; **сессии-воркеры НЕ открывать, пока разрез не прошёл pre-flight** (все ответы «да»). Мелкая/тесно-связанная задача → одна сессия, промпт не нужен (ak47-simplicity [internal]).

## Мета-промпт (копировать лид-сессии)

```
Ты — лид декомпозиции сложной задачи. Твоя задача НЕ выдать общий список подзадач.
Твоя задача — решить, можно ли безопасно разбить это на независимые параллельные LLM-сессии,
и если да — выдать пакеты частей, устойчивые к коллизиям.

Правила:
- Оператор будет вести 3–5 параллельных сессий. Он не-технарь: тяжёлую работу делаешь ты.
- Имплементеры НЕ подтверждают «готово» сами; потом будет ревью со свежим контекстом.
- Предпочитай МЕНЬШЕ по-настоящему независимых частей, чем много связанных.
- Если задача слишком связана — прямо скажи «НЕ ПАРАЛЛЕЛИТЬ» и объясни почему.

ЗАДАЧА:
<вставить задачу>

ИЗВЕСТНЫЙ КОНТЕКСТ / НЕ-ЦЕЛИ / детали репо:
<вставить контекст>

Выдай по порядку:

1. ПОНИМАНИЕ ЗАДАЧИ: цель · не-цели · неизвестное · допущения.

2. КАРТА ЗАВИСИМОСТЕЙ / СВЯЗАННОСТИ (главное — не список задач, а граф!):
   для кода: вероятно затрагиваемые файлы/модули · общие конфиги/схемы/миграции/фикстуры ·
             публичные интерфейсы · «hub»-файлы (глобальные утилиты) · какие тесты упадут.
   для знаниевой работы: ключевые утверждения · классы источников · понятия, требующие
             единого определения · секции результата · вероятные противоречия.

3. КАНДИДАТЫ РАЗРЕЗА (>=3, для каждого — плюсы, скрытая связанность, риск merge, стратегия проверки):
   - по графу зависимостей (кластеры связности, минимум меж-частных рёбер);
   - contract-first (заморозить API/схему/интерфейс, части работают против мока);
   - по владению доменом/данными end-to-end (вертикаль, НЕ слои бэкенд/фронт/тесты);
   - слоёный — только если контракт уже заморожен.

4. ВЫБРАННЫЙ РАЗРЕЗ (или «НЕ ПАРАЛЛЕЛИТЬ») + почему отвергнуты другие кандидаты.

5. PRE-FLIGHT ТАБЛИЦА КОЛЛИЗИЙ — по каждой ПАРЕ частей:
   | пара | общие файлы записи | общие решения | общие фикстуры/источники | скрытая связь | митигация | проходит? |
   Провалить разрез, если у пары есть: общий файл записи · общее решение об API/схеме ·
   общая миграция/конфиг/фикстура · общее UX-состояние · общая терминология ·
   неясный порядок merge · проверка, зависящая от завершения соседа.

6. СОСТЯЗАТЕЛЬНЫЙ ВОПРОС — для каждой пары ответь буквально:
   «Как часть A может МОЛЧА сломать часть B, даже если они никогда не трогают один файл?»
   (сменила семантику экспортируемого типа · обе назвали одно понятие по-разному ·
    обе добавили конкурирующий хелпер · изменила поведение по умолчанию без правки тестов…)
   Не можешь ответить — ты не понял разрез, вернись к шагу 2.

7. ЗАМОРОЖЕННЫЕ КОНТРАКТЫ (зафиксировать ДО спавна): имена API/типов/маршрутов/ошибок ·
   поля БД · порядок миграций · UX-состояния · имена логов/телеметрии · владение фикстурами ·
   владение источниками (для ресёрча) · стиль/терминология.
   Если контракт пока неизвестен — вместо параллели создай ПОСЛЕДОВАТЕЛЬНУЮ задачу
   «выработать контракт», и только потом параллель.

8. ПАКЕТЫ ЧАСТЕЙ (по одному на сессию): миссия · владеемые файлы · read-only контекст ·
   ЗАПРЕЩЁННЫЕ файлы · входы · выходы · замороженные контракты · локальная проверка (команды) ·
   не-цели · триггеры эскалации · критерий «готово» (доказуемый, без self-certify) ·
   точный seed-промпт для воркер-сессии.

9. ПЛАН ИНТЕГРАЦИИ: кто владелец merge (отдельная сессия, НЕ имплементеры) · порядок merge ·
   проверки после каждого merge · финальная верификация · риски отката.

10. ПРАВИЛА ЖИЗНЕННОГО ЦИКЛА — конкретные триггеры для: локального ре-разреза · глобального
    ре-разреза · промоушена части в самостоятельную задачу · слияния двух потоков ·
    сериализации · отмены.

САМО-КРИТИКА (перед финалом — атакуй свой разрез):
- Где вероятнее всего скрытая связанность? Какая пара частей самая опасная?
- Какие неявные решения могут разойтись? Какая часть скорее всего разрастётся?
- Что заставит этот разрез провалиться на merge?
Перепиши план ОДИН раз после само-критики.
Запрет отговорок: НЕ предлагай «просто быстро поправлю общий конфиг/переименую для ясности».
```

## Pre-flight чек-лист (все «да» → можно спавнить)
- [ ] У каждой части — **эксклюзивные** владеемые файлы/секции.
- [ ] Общие файлы записи имеют ровно **одного** владельца (или обрабатываются последовательно).
- [ ] «Hub»-файлы (глобальные утилиты/роутер/конфиг) — один владелец или serial.
- [ ] Граф прогнан на **циклы** (A↔B) — циклов нет, топологический порядок есть.
- [ ] Общие имена API/типов/ошибок **заморожены**; фикстуры и источники имеют владельца.
- [ ] Каждая часть проверяется **локально**, не дожидаясь соседа.
- [ ] Определены триггеры promote / merge / ре-разрез и **порядок интеграции**.
- [ ] Есть минимальный дашборд (строка на часть) и формат чек-ина.
- **Вердикт:** спавнить · ре-резать · сериализовать · сперва задача-«контракт».

## Ранние сигналы плохого разреза (пауза, если воркер говорит)
«мне нужно править файл вне моих» · «я предположил, что API выглядит так…» · «я сделал хелпер, похожий на…» · «это зависит от того, что решит другая сессия» · «я поменял общий конфиг/схему/роутер» · «я обновил тесты глобально» · «я отрефакторил заодно» · «проверить не смог, но должно работать» · «я переименовал понятие для ясности» · «мелких конфликтов много, но вроде лёгкие» · «готово» без вывода команд/списка/диффа.
> Правило для не-технаря: **если две сессии вот-вот примут одно и то же решение — останови обе и сделай микро-задачу «согласовать контракт».**

## Границы (АК-47)
Полный аппарат — для КРУПНОГО (много файлов/частей). Для 2–3 частей достаточно шагов 4–6 (выбор разреза + таблица коллизий + состязательный вопрос) на один экран. Не превращать pre-flight в бюрократию.
